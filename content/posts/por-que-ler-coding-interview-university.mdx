Existe um repositório no GitHub chamado [Coding Interview University](https://github.com/jwasham/coding-interview-university#dont-feel-you-arent-smart-enough).

À primeira vista, ele parece só mais uma lista gigante de estudos para entrevista técnica.

Mas eu acho que a melhor forma de ler esse repo não é como uma lista de "como passar no Google", "como entrar na Amazon" ou "como decorar algoritmos".

Eu leria como um mapa.

Um mapa para responder uma pergunta que muita gente que programa carrega por anos:

**o que eu preciso estudar para ter uma base mais sólida em Ciência da Computação e Engenharia de Software?**

### O valor do repo não está só nas entrevistas

O autor criou o plano como uma lista de estudos para se tornar software engineer em grandes empresas. Depois de seguir esse plano, ele foi contratado como Software Development Engineer na Amazon.

Isso por si só já chama atenção.

Mas o que torna o repositório interessante é outra coisa: ele organiza, em uma sequência prática, muitos assuntos que normalmente aparecem espalhados em faculdade, livros, vídeos, cursos e experiência de trabalho.

Tem Big-O, estruturas de dados, arrays, listas ligadas, pilhas, filas, hash tables, árvores, heaps, grafos, ordenação, recursão, programação dinâmica, processos, threads, cache, redes, testes, design de sistemas e vários tópicos extras.

Se você programa há algum tempo, provavelmente já usou várias dessas coisas sem parar para estudar como elas funcionam por baixo.

E tudo bem.

Boa parte do desenvolvimento moderno é justamente usar abstrações boas.

O problema começa quando a abstração vira cegueira.

Você usa `Array`, `Map`, banco de dados, cache, fila, HTTP, framework, ORM, cloud, mas nunca parou para entender custo, trade-off, memória, concorrência, latência, complexidade e comportamento em escala.

Esse repo ajuda a enxergar o chão onde as ferramentas pisam.

### "Não sou inteligente o bastante"

Uma das seções mais importantes do repositório é justamente a âncora do link que me fez querer escrever este post: **"Don't feel you aren't smart enough"**.

A ideia é simples e verdadeira: muitos bons engenheiros têm a insegurança de não serem inteligentes o bastante.

Isso bate forte porque a área de tecnologia tem uma cultura estranha.

De um lado, ela vende a ideia de que qualquer pessoa pode aprender.

Do outro, ela glorifica o "gênio", a pessoa que resolve algoritmo de cabeça, entende paper em uma sentada, programa compilador no fim de semana e parece nunca ter dúvida.

Na prática, a maioria das pessoas boas que eu conheço estudou muito, errou muito, demorou para entender várias coisas e precisou rever fundamentos várias vezes.

Base técnica não nasce pronta.

Base técnica é construída.

E é por isso que esse repositório é útil: ele tira um pouco do misticismo. Ele mostra que existe um conjunto de assuntos, existe uma ordem possível, existem recursos, existe prática e existe repetição.

Não é mágica.

É treino.

### Leia como mapa, não como sentença

O Coding Interview University é grande.

Grande mesmo.

Se você abrir o repositório achando que precisa estudar tudo antes de se considerar uma pessoa desenvolvedora de verdade, você provavelmente vai se frustrar.

Eu não recomendo essa leitura.

Eu leria assim:

1. **como diagnóstico**
   Veja os tópicos e marque o que você conhece, o que conhece superficialmente e o que nunca estudou.

2. **como trilha de fundamentos**
   Escolha um tema por vez. Big-O, arrays, hash tables, árvores, grafos. Não tente abraçar tudo na mesma semana.

3. **como guia de prática**
   O próprio repo insiste em um ponto importante: faça problemas enquanto aprende. Não deixe para praticar só depois de "terminar a teoria".

4. **como referência de longo prazo**
   Você pode voltar nesse material em momentos diferentes da carreira. O que parece abstrato hoje pode fazer sentido depois de lidar com performance, banco, cache, fila ou sistemas distribuídos no trabalho real.

### O melhor uso: estudar para entender, não para performar

Preparação para entrevista pode virar teatro.

A pessoa decora padrões, faz LeetCode em massa, aprende a narrar raciocínio e às vezes passa sem necessariamente ter absorvido bem os fundamentos.

Isso acontece.

Mas também existe o caminho bom: usar a entrevista como desculpa para estudar coisas que vão melhorar sua engenharia no dia a dia.

Quando você entende complexidade, você pensa melhor antes de percorrer uma lista dentro de outra lista.

Quando entende hash table, você entende melhor por que certas buscas são rápidas e por que colisão existe.

Quando entende árvore, heap e grafo, você começa a reconhecer estruturas escondidas em problemas reais.

Quando entende cache, processo, thread e rede, você começa a olhar para aplicações web com menos ingenuidade.

E quando entende system design, você para de discutir arquitetura como preferência estética e começa a discutir trade-offs.

Esse é o ponto.

O objetivo não é virar uma pessoa que responde entrevista bonito.

O objetivo é virar uma pessoa que entende melhor o software que escreve.

### Com IA, fundamentos ficaram ainda mais importantes

Hoje, com Copilot, Cursor, ChatGPT e agentes de código, ficou mais fácil gerar solução.

Mas ficou mais importante saber avaliar solução.

Um agente pode escrever uma função que parece correta.

Mas você ainda precisa perceber se a complexidade explode, se a estrutura de dados faz sentido, se o algoritmo está frágil, se tem problema de concorrência, se o banco vai sofrer, se a API está acoplando demais ou se a solução só passou no exemplo feliz.

Fundamento virou uma espécie de radar.

Quanto melhor sua base, melhor você usa IA.

Você deixa de ser apenas alguém que aceita código gerado e passa a ser alguém que dirige, critica, corrige e melhora o resultado.

### Por onde começar

Se eu fosse começar hoje, usaria o repo assim:

1. Ler a introdução e a seção ["Why use it?"](https://github.com/jwasham/coding-interview-university#why-use-it).
2. Ler a seção ["Don't feel you aren't smart enough"](https://github.com/jwasham/coding-interview-university#dont-feel-you-arent-smart-enough) com calma.
3. Escolher uma linguagem para praticar. Python, Java, C++ ou a linguagem que você já usa bem.
4. Estudar Big-O e estruturas de dados básicas.
5. Implementar algumas estruturas do zero, mesmo que no trabalho você use a versão pronta da linguagem.
6. Resolver poucos problemas por tema, mas resolver de verdade.
7. Revisar depois de alguns dias. Sem revisão, a sensação de aprendizado engana.

Não precisa fazer 8 horas por dia.

Não precisa transformar sua vida em um bootcamp infinito.

Mas precisa de consistência.

### O que esse repo não é

Ele não é um substituto para experiência real.

Ele não ensina tudo sobre produto, manutenção, legado, observabilidade, comunicação, deploy, incidentes, times, negócio ou escrita de software em produção.

Também não é uma trilha específica de frontend, backend, mobile ou full stack.

O próprio README deixa claro que o foco é preparação de base para engenharia de software e entrevistas técnicas, não uma formação completa em todas as áreas do desenvolvimento moderno.

Isso é bom.

Um material não precisa cobrir tudo para ser valioso.

Ele precisa deixar claro o que cobre.

### Minha recomendação

Leia o [Coding Interview University](https://github.com/jwasham/coding-interview-university#dont-feel-you-arent-smart-enough) se você quer fortalecer fundamentos.

Leia se você sente que sabe programar, mas ainda tem buracos em algoritmos, estruturas de dados e Ciência da Computação.

Leia se você está se preparando para entrevistas, mas não quer estudar só para passar em entrevista.

Leia principalmente se você já teve aquela sensação de:

"acho que todo mundo sabe isso, menos eu."

Provavelmente não.

Muita gente está no mesmo ponto, só que em silêncio.

Esse repo é um bom lembrete de que estudar base não é prova de fraqueza.

É parte do ofício.
