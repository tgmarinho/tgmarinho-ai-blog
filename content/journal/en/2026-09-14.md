Today was less about shipping and more about thinking through a data model problem that keeps coming back: how to properly represent corporate groups (a parent company and its subsidiaries) inside a multi-tenant application.

### Framing the requirement

I started by opening an issue from an existing spec about "grupos de empresas." The document lays out the case where a single tenant is not just one company but a network of related entities, each with its own operational data yet sharing a common umbrella.

### Weighing implementation options

Option A felt like the best fit for the requirement, but the implementation path was not obvious. The core question: is it enough to keep an `empresa_id` on every table, or do I also need a `grupo_id` alongside it? Denormalizing the group reference gives faster queries and simpler row-level filtering, but it also means every write path has to keep both columns in sync. Keeping only `empresa_id` and joining up to the group is cleaner conceptually but heavier at read time.

### Prototyping to see it

I asked for a concrete implementation to look at, precisely because reading a spec is not the same as feeling how the migration would land. Moving an already-populated schema toward this shape is not a one-shot change - it is a coordinated migration across tables, indexes, and access patterns.

I also revisited what had been written previously about "matriz e filial" to align terminology before committing to a direction.
