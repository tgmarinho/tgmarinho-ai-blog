Today was about getting ephemeral environments right. I spent the session digging into how Railway's PR Preview actually behaves end to end, especially around database isolation.

### curitiba-v1

The core question I wanted to answer: does a fresh database get provisioned on every new PR, or are previews sharing state? That matters a lot, because the whole point of PR previews is reversible, disposable context — if the DB bleeds across branches, the model falls apart.

To test it, I opened a throwaway PR (`fc24554e`) that spins up backend, frontend, and database together as a Railway PR Preview. Watching it come up gave me the signal I needed to move forward.

From there I shifted into planning mode: how staging should connect to a single demo tenant on a production third-party integration (read-only, scoped to one company), and how the environments should be wired in GitHub to match. I consolidated that into a single plan and started executing it — configuring the GitHub environments to mirror the Railway topology, so promotion between preview, staging, and production stays explicit.

Still early, but this is exactly the kind of infra work that pays back later: cheap, isolated, agent-friendly environments where I can run experiments without worrying about leaking state between branches. More to validate tomorrow once the plan is fully in place.
