# Vision

tgmarinho-ai-website exists so that Thiago Marinho has one public home for his engineering identity, writing, daily work record, and ways to collaborate.
It serves readers, recruiters, collaborators, and AI agents that need an accurate public model of his work.
It turns Git-tracked content and profile data into a bilingual, fast, searchable, and citeable web presence.
It owns exactly one thing: the public representation of Thiago Marinho on tgmarinhopro.com.

## Public Identity Is A Product Surface

The site accepts changes that make the author easier to understand, contact, cite, or hire.
The institutional pages, CV, projects, links, landing page, and contact paths stay consistent with siteConfig and localized messages.
Proof belongs in real projects, posts, experience, metrics, and public links, not inflated claims.
The site may sell the author's work, but it does it with evidence and direct routes to act.
A change is incomplete when it updates a visible claim in one locale, page, metadata block, or generated corpus while leaving another stale.

## Content Lives In Git

Posts, interactive posts, and journal entries are source files under content, reviewed through the same repository workflow as code.
Velite is the content boundary because schema validation and typed output are part of the publishing contract.
The site refuses a CMS, runtime MDX parsing for normal posts, and hand edits to generated Velite output.
A post pair is one editorial unit: shared date, shared translationKey, shared cover intent, and aligned practical conclusion.
The one-article-per-day convention keeps the archive legible and remains part of the acceptance criteria for new posts.
Generated llms corpus files and SEO surfaces must reflect large content changes before the change is considered done.

## Bilingual Means Mirrored Intent

Portuguese is the default public locale and English is a first-class version, not an afterthought.
Routes, UI strings, article pairs, daily entries, metadata, and sitemap behavior move together when a feature is localized.
The translations do not need to be literal, but they must carry the same facts, tone, privacy boundary, and user promise.
A bilingual feature may ship only when language switching, canonical URLs, hreflang behavior, and public labels stay coherent.
The site resists partial localization that makes one language more current, more private, or more persuasive than the other.

## Agentic Work Is Published With Boundaries

The site treats AI agents as tools, readers, and subject matter.
It welcomes features like Ask Thiago, llms.txt, structured data, public retrieval over published corpus, and posts about agent workflows when they clarify public knowledge.
It does not turn private session logs, memories, secrets, client data, or personal life into public content.
The daily journal is generated from work traces, then filtered, mirrored, and published only when it preserves privacy and names real project themes.
Agent-assisted implementation is acceptable when the resulting code, prose, tests, and PR evidence can stand without the agent.

## Design Carries Authority Without Noise

The visual system stays Agentic Futurist: dark canvas, restrained cyan and magenta accents, technical UI, and editorial typography inside posts.
Motion, glass, particles, or AI signals are welcome when they support comprehension, status, or identity.
Ornament is resisted when it competes with reading, damages accessibility, slows the site, or copies another person's persona.
Design changes that alter tokens, prose, hero structure, or the reading experience update the visual changelog.
The site keeps reduced motion, readable narrow viewports, local image discipline, and print friendly CV behavior as product requirements.

## Static First, Measured Where It Matters

The default architecture is static-first App Router with Server Components and small client islands for interactivity.
Client code is justified by user interaction, browser APIs, analytics, search, forms, or motion that cannot live on the server.
APIs may exist, but volatile in-memory behavior is marked as provisional until a durable store is configured.
Analytics, SEO, answer-engine optimization, structured data, RSS, sitemap, robots, and llms files are product surfaces because they shape how humans and agents find the work.
New dependencies and runtime services are accepted only when they strengthen the public surface enough to justify the operational cost.

## Scope

This project is not a CMS, not a social network, not a private knowledge base, not a general analytics platform, and not a multi-tenant product.
It is not the place for secrets, unpublished client context, job-application specifics, personal memories, or raw agent transcripts.
It is not a playground for stack swaps that replace the App Router, Velite, Tailwind, next-intl, Bun, or Vercel without an explicit decision.
It may host focused experiments when they serve the author's public identity, explain a technical idea, or improve the reader's path.
A change aligns when it strengthens the public identity, preserves the bilingual contract, respects the Git content model, and keeps the site fast, private, and AI-readable.
A change should be resisted when it adds surface area without evidence, fragments localization, weakens privacy, hides state in vendors, or makes the design louder than the substance.
